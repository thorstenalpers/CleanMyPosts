# Frontend Conventions

## Two build targets

Vite produces two independent bundles from the same `src/` tree:

| Target    | Entry                  | Output              | Runs in                   |
|-----------|------------------------|---------------------|---------------------------|
| `chrome`  | `src/main.ts`          | `dist/chrome/`      | ChromeWebView (app UI)    |
| `content` | `src/content-entry.ts` | `dist/content/`     | SiteWebView (x.com, etc.) |

The content bundle is a self-contained IIFE. It must import nothing that assumes a normal
browser environment (no `document.querySelector` on module load, no globals that clash with
the host page).

## Svelte 5

- Runes only: `$state`, `$derived`, `$effect`, `$props`. No `export let` props, no `$:`
  statements, no legacy stores.
- `$effect` is the exception, not the default. Prefer `$derived` for computed state.
- Stores live in `src/lib/stores/*.svelte.ts` and export an object with getters — not loose
  `let` exports that lose reactivity on import.
- File names `kebab-case.svelte`, component names in templates `PascalCase`.

## Component layers

| Location                    | Rule                                             |
|-----------------------------|--------------------------------------------------|
| `src/lib/components/ui/`    | generated by shadcn-svelte; document any changes |
| `src/lib/components/`       | app components — **bridge-free, store-free, one `.stories.svelte` each** |
| `src/views/`                | pages — may read stores, not call bridge directly|
| `src/lib/engine/`           | delete engine — no bridge, no component imports  |

A component that needs the bridge to render can neither appear in Storybook nor be tested in
isolation — that is the whole reason for the bridge-free rule. Views are the seam: a view
reads the stores and passes plain props into a bridge-free component, and handles the
component's events by calling the bridge. Keep the logic-free presentation in the component.

## Storybook — mandatory

**Every component in `src/lib/components/` has a `.stories.svelte` next to it**
(`sidebar-shell.svelte` → `sidebar-shell.stories.svelte`), authored with
`@storybook/addon-svelte-csf`. Without a story the component counts as unfinished. This
explicitly includes the **left navbar / sidebar**.

**Settings gets a story too.** The settings *view* is bridge-connected and stays out of
Storybook, but its form is a bridge-free `settings-form` component (props: current
`AppSettings`; event: `change` with the new settings). That component carries the story; the
view is a thin wrapper that loads `settings.get` and sends `settings.set`. Apply the same
split to any other view whose body is worth previewing in isolation.

### Required story states

Every component that shows data needs at least:

1. `Default`
2. `Empty` — with the real text the user sees, where an empty state exists
3. `LongContent` — overlong labels, long handles, five-digit counts
4. the component's specific edge case (running action, disabled, collapsed sidebar, login not
   detected, confirmation dialog open)

### Setup

- `addon-a11y` is on; a11y violations count as errors, not hints.
- A decorator renders each story in light and dark; both must hold up (the app is
  theme-aware).
- Storybook points the bridge at `mock.ts` and never talks to a real host.
- Shared sample data lives in `src/lib/fixtures/` and is used by stories **and** tests — no
  story with ad-hoc invented data.

## shadcn-svelte

- Existing components first. Use `npx shadcn-svelte@latest add` instead of hand-rolling.
- Compose instead of reinventing: settings page = form controls inside Cards.
- Built-in variants (`variant="outline"`, `size="sm"`) before custom classes.
- Import style: multi-part as a namespace
  (`import * as Card from '$lib/components/ui/card'`), single as a named import
  (`import { Button } from '$lib/components/ui/button'`).

## TypeScript

- `strict`. No `any`, no `as` to silence the compiler.
- Zod schemas are the type source: `z.infer`, no hand-maintained parallel interfaces.
- Exported functions have explicit return types.
- Selectors in engine modules are named `const` strings at the top of the file.

## Mock bridge

`src/lib/bridge/mock.ts` implements every method in `BridgeMethods`. It is used by
`npm run dev` and by Vitest component tests. A new bridge method without a mock entry
breaks both.

## Tests

Vitest with happy-dom and `@testing-library/svelte`, test file next to the source
(`x-view.svelte` → `x-view.test.ts`). Test via visible text and roles, not CSS classes
or component internals.

Engine modules are tested against fixture HTML files (real, trimmed page markup saved from
the live site) — never against the live site.
