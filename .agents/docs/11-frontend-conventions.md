# Frontend Conventions

## Two build targets

Vite produces two independent bundles from the same `src/` tree:

| Target    | Entry                  | Config                       | Output          | Runs in                 |
| --------- | ---------------------- | ---------------------------- | --------------- | ----------------------- |
| `chrome`  | `src/routes/`          | `vite.config.ts` (SvelteKit) | `build/`        | chrome webview (app UI) |
| `content` | `src/content-entry.ts` | `vite.content.config.ts`     | `dist/content/` | site webview (x.com, …) |

**The content build must never see the SvelteKit plugin.** It runs inside a foreign document
on x.com; anything `$app/*` pulls in would break there, and it would break silently, mid-run.
That is why it keeps its own Vite config instead of a second entry in the main one.

The content bundle is a self-contained IIFE. It must import nothing that assumes a normal
browser environment (no `document.querySelector` on module load, no globals that clash with
the host page).

## Svelte 5

- Runes only: `$state`, `$derived`, `$effect`, `$props`. No `export let` props, no `$:`
  statements, no legacy stores.
- `$effect` is the exception, not the default. Prefer `$derived` for computed state.
- Never write state that another library owns from inside an `$effect` body (e.g.
  `mode-watcher`'s `setMode`) — Svelte 5 rejects a state write while effects are flushing and
  logs `updated at $effect`. Defer it with `queueMicrotask`. Bridge calls _are_ fine in an
  effect: `BridgeClient` keeps its pending map in a plain `Map`, not in `$state`.
- Stores live in `src/lib/stores/*.svelte.ts` and export an object with getters — not loose
  `let` exports that lose reactivity on import.
- File names `kebab-case.svelte`, component names in templates `PascalCase`.

## Component layers

| Location                 | Rule                                                    |
| ------------------------ | ------------------------------------------------------- |
| `src/lib/components/ui/` | generated by shadcn-svelte; document any changes        |
| `src/lib/components/`    | app components — **bridge-free, store-free**            |
| `src/lib/views/`         | view bodies — may read stores, not call bridge directly |
| `src/routes/`            | SvelteKit routes — a layout and one thin page per view  |
| `src/lib/engine/`        | delete engine — no bridge, no component imports         |

A component that needs the bridge to render cannot be tested in isolation — that is the
whole reason for the bridge-free rule. Views are the seam: a view reads the stores and passes
plain props into a bridge-free component, and handles the component's events by calling the
bridge. Keep the logic-free presentation in the component.

## Routing

`+layout.svelte` owns the bridge, the four stores, and the sidebar, and hands them down
through `$lib/app-context.ts`. A `+page.svelte` is a two-line file: pull what it needs out of
the context, render the matching view.

The active nav item is derived from `page.url.pathname`, never from local state — otherwise
the sidebar and the URL can disagree.

**Routing unmounts a page.** Anything the user would be annoyed to lose on a tab switch —
filters, sort order, selections — belongs in a store, not in the page component. `LogStore`
holds the log filters for exactly this reason.

## shadcn-svelte

- Existing components first. Use `npx shadcn-svelte@latest add` instead of hand-rolling.
- Compose instead of reinventing: the settings page is form controls inside
  `setting-section` / `setting-row`, not bespoke layout per screen.
- Small primitives the registry does not carry (`badge`, `progress`) are written by hand into
  `ui/` in the same style rather than pulling in a dependency for twenty lines.
- Built-in variants (`variant="outline"`, `size="sm"`) before custom classes.
- Import style: multi-part as a namespace
  (`import * as Card from '$lib/components/ui/card'`), single as a named import
  (`import { Button } from '$lib/components/ui/button'`).

## TypeScript

- `strict`. No `any`, no `as` to silence the compiler.
- Zod schemas are the type source: `z.infer`, no hand-maintained parallel interfaces.
- Exported functions have explicit return types.
- Selectors in engine modules are named `const` strings at the top of the file.

## Mock bridge

`src/lib/bridge/mock.ts` implements every method in `BridgeMethods`. It is used by
`npm run dev` and by Vitest component tests. A new bridge method without a mock entry
breaks both.

## Tests

Vitest with happy-dom and `@testing-library/svelte`, test file next to the source
(`x-view.svelte` → `x-view.test.ts`). Test via visible text and roles, not CSS classes
or component internals.

Engine modules are tested against fixture HTML files (real, trimmed page markup saved from
the live site) — never against the live site.
